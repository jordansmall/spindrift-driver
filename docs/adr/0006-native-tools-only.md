# Tools are native to the Driver: no MCP, and anything else is a CLI on PATH

The Driver's Tools are compiled into the Driver: `bash`, `edit`, `write`, and `subagent` when the roster holds at least one Agent File. There is no MCP anywhere in this design — neither an MCP server the Driver exposes to other agents nor an MCP client it calls out to — and no plugin system, dynamic tool protocol or negotiated capability list standing in its place. A Tool is a function in this binary, offered in the request's `tools` array and dispatched by name, or it is not a Tool.

Anything the Model needs that is not one of those four is a CLI on PATH, reached through the Bash Tool. The Box already ships a shell and a filesystem, so that route is already universal: whatever a host can install into the Box, the Model can run. A second route to the same capabilities would have to bring its own transport, its own schema discovery and its own error semantics to buy, for every capability somebody packages as a server, what `bash` already provides for everything else.

The reason is the Guard chain, and it outranks convenience. A native Tool passes the pre-call Guard Hooks in manifest order and reports the standard event pair on the way out — one `tool_target`, one `is_error` verdict — and a file Tool is presented to that chain as the `Read` shape, so the credential-path deny a host already wrote covers `edit` and `write` exactly as it covers a read. A tool arriving over MCP brings semantics the Driver does not own: its arguments are neither a command nor a path, so there is no single shape in which the Driver could hand the call to the same chain before it runs, and a deny would have to learn each server's argument grammar to stay meaningful. An unguarded capability path is exactly what the Guard Hooks seam exists to make impossible, so a capability that cannot be put in front of the chain in one shape is refused here rather than left to whoever writes the hook.

The Tool set is a contract, not a configuration. The host-side Strategy watches the stable `write` tool name in the event stream to decide that a run changed files instead of describing changing them, so which Tools exist is part of what this Driver promises its host — the same kind of promise as the event grammar of ADR-0004, and just as fixed by the binary rather than by the run. Which Tools exist therefore changes by a code change, a Driver release, not a setting a host or a Box can turn: nothing in the Driver Config, the roster or the Target repo adds a Tool, which is the same rule that keeps the repository under repair from configuring the run that repairs it.

The cost is stated honestly: adding a Tool means changing and releasing the Driver, and there is no third-party Tool ecosystem here and none can arrive. Accepted, because each alternative costs more than it returns — a capability path outside the Guard chain, a stream of calls the Driver can no longer report as calls, and a runtime that loads third-party protocol code, which ends ADR-0001's standard-library-only rule along with the auditability that rule buys.

## Considered Options

- **An MCP server the Driver exposes, so a host could offer its Tools to other agents** — rejected: the Driver is a subprocess with one stdout contract and no business serving anybody else, and exposing its Tools would publish the very file writes the host is guarding to whatever can reach it.
- **An MCP client in the Driver, reaching third-party servers** — rejected: the Model could then call a tool whose arguments the pre-call chain has no shape for, and the Driver would own the transport, the discovery and the failure modes of every server a Box happens to point at.
- **A config- or manifest-declared tool list** — rejected: which Tools exist is the Driver's contract with its host, so a set declared in data would let a file the run reads — the Driver Config, the roster, the checkout — add a capability the operator's guards were written before.
- **A capability protocol alongside a CLI on PATH through the Bash Tool** — rejected: the Box already ships a shell and a filesystem, so the second route needs its own transport, schema discovery and error semantics to buy what `bash` already provides, and it cannot put its calls in front of the Guard chain.
